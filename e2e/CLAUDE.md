# CLAUDE.md — e2e

Chrome end-to-end tests with golden-screenshot comparison. See `../CLAUDE.md` for
repo-wide context.

```bash
pnpm install            # first time; downloads Chrome via puppeteer's postinstall
npm test                # compare against goldens, exit 1 on drift
npm run update-goldens  # rewrite goldens from this run
npm run headed          # watch it in a visible browser
```

**Build the frontend first** — the runner serves `frontend/public`, it does not build it:

```bash
cd ../frontend && npm run build-dev
```

## What it does

`run.mjs` spins up a complete, throwaway system per run: a temp data directory, a free
port, `cargo run` of the real backend, and a real Chrome. Nothing touches
`backend/bug-data`, and the temp directory is removed afterwards.

The bootstrap admin password is generated by the backend, printed once, and never
recoverable — so the runner scrapes it from stdout exactly as a human would, then drives
the whole first-login flow with it.

Steps, in capture order:

| # | Screenshot | What it proves |
|---|---|---|
| 1 | `login-screen` | Username **and password** fields render |
| 2 | `login-rejected` | A wrong password shows an error and does not sign in |
| 3 | `forced-password-change` | The generated password lands on the rotation screen, not the app |
| 4 | `password-too-short` | Client-side validation fires before any request |
| 5 | `back-to-login-after-change` | A successful change revokes the session and returns to sign-in |
| 6 | `signed-in-home` | The new password works and the app renders |
| 7 | `session-persists-after-reload` | The stored session survives a reload |

It also asserts non-visual behaviour that a screenshot cannot capture: after rotation the
original bootstrap password must be rejected with 401.

## Goldens

Filenames carry the capture-order number (`03-forced-password-change.png`) so the
sequence is readable from a directory listing and an inserted step is obvious.

Goldens are committed; `output/` (actual captures plus `*-diff.png` for any mismatch) is
gitignored. A run tolerates up to 40 differing pixels for antialiasing — enough to absorb
font rasterisation noise, far too few to hide a real layout change. Verified: the runs
are pixel-identical back to back (0 px), and changing one line of copy failed three
screenshots with 563 px each.

Screenshots are only as stable as what they capture. `run.mjs` freezes CSS animations and
transitions and hides the text caret before every capture; if you add a step showing
timestamps, generated ids, or anything else that varies per run, it will flake.

**Regenerate goldens deliberately, never reflexively.** `npm run update-goldens` accepts
whatever is on screen as correct — look at the diff image first and confirm the change is
one you meant to make.
